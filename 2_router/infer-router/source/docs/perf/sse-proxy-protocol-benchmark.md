# SSE Proxy 协议选型基准测试报告

> 测试目的：评估 OneRouter 在 Client → Router(Proxy) → GPU Backend 全链路中，不同前后端 HTTP 协议组合对 SSE 流式传输的性能影响，为协议选型提供数据支撑。

## 一、选型建议 (TL;DR)

### 快速决策表

| 部署场景 | 推荐方案 | TTFT | 吞吐量 | 理由 |
|---------|---------|------|--------|------|
| **内网全链路可控** | **h2c→h2c** | 2~10ms | 高 | TTFT 最优、P99 最低、goroutine 最少、零失败 |
| 后端不支持 h2c | h2c→h1 | 12~18ms | **最高** | 前端 h2c 多路复用 + h1 后端简单字节流 |
| 前端需兼容旧客户端 | h1→h2c | 5~9ms | 中高 | 后端 h2c 消除 HOL Blocking，前端保持兼容性 |
| 纯 HTTP/1.1 环境 | h1→h1 | 3~1147ms | 低 | 仅限轻量场景，大数据量严重退化 |
| 长连接单流场景 | hijack→h2c | 5~27ms | 中 | TCP_NODELAY 降低单流延迟，但**不适合短连接** |

### 按业务场景推荐

**场景 1：LLM 推理网关 (典型 200~1000 tokens，高并发)**
```
推荐：h2c→h2c
原因：TTFT 2.4ms (h1→h1 需 225ms)，用户体感延迟低 94 倍
      P99 1.69s (h1→h1 需 6.90s)，SLA 可控
      GR Delta 接近 0，无 goroutine 泄漏风险
```

**场景 2：代码生成 / 长文本 (500~10000 tokens，中并发)**
```
推荐：h2c→h2c，退而求其次 h2c→h1
原因：大数据量下 h1 后端 HOL Blocking 严重
      h1→h1 在 xlarge(1Ktok) 仅 85 Req/s，h2c→h1 达 423 Req/s (+397%)
      h1→h1 在 xxlarge(10Ktok)/10K 出现 49 个超时失败
```

**场景 3：轻量 API 网关 (短回答 <100 tokens)**
```
推荐：任意方案均可，差异 <5%
原因：瓶颈在后端推理时间 (~250ms)，协议开销占比极小
      但 h2c→h2c 的 P99 尾延迟仍然最优 (289ms vs 329ms)
```

**场景 4：前端必须 HTTP/1.1 (兼容性要求)**
```
推荐：h1→h2c
原因：仅升级后端即可获得 66%~79% 吞吐提升
      TTFT 从 162ms 降至 4.6ms (heavy/10K)
      不需要改动任何客户端代码
```

**场景 5：不建议使用 Hijack**
```
除非是长期保持的单一 SSE 长连接 (如 WebSocket 替代场景)。
Hijack 杀死 HTTP Keep-Alive，每次请求新建 TCP 连接。
在 heavy/10K 场景出现 10 个失败，TTFT 238ms (h1→h1 仅 162ms)。
```

### 协议升级优先级

如果只能做一步改造，**优先升级后端到 h2c**：
- h1→h1 → h1→h2c：吞吐 +66~79%，TTFT 降 35~97%，零代码改动前端
- h1→h2c → h2c→h2c：进一步降低 TTFT，改善 P99，需要前端支持 h2

## 二、大模型推理场景协议选型

不同的大模型应用场景在 tokens 数量、并发模式、延迟敏感度上差异巨大，需要针对性选择协议。

### 场景全景图

| 场景 | 输出 Tokens | 输入 Tokens | 并发特征 | TTFT 敏感度 | 吞吐敏感度 | 请求持续时间 | 对应测试级别 |
|------|-----------|-----------|---------|------------|-----------|------------|------------|
| 聊天对话 | 50~300 | 100~2K | 高并发、短连接 | **极高** (用户在等) | 中 | 0.3~2s | light~medium |
| RAG 问答 | 100~500 | 2K~8K | 中并发 | **高** | 中 | 0.5~3s | medium~heavy |
| SWE (代码生成/补全) | 200~2000 | 4K~32K | 中高并发、突发 | **极高** (IDE 内等待) | **高** | 1~10s | medium~xlarge |
| SWE (代码审查/重构) | 500~5000 | 8K~128K | 低并发 | 中 | 中 | 3~30s | heavy~xxlarge |
| Agentic (Tool Use) | 50~500/轮 | 2K~32K | **极高并发** (多轮×多Agent) | **极高** (链式调用) | **极高** | 0.5~5s/轮 | light~heavy |
| Agentic RL (训练) | 200~2000 | 4K~64K | **超高并发** (batch rollout) | 低 | **极高** | 1~20s | medium~xlarge |
| 长文本摘要 | 500~3000 | 32K~200K | 低并发 | 低 | 中 | 5~60s | heavy~xxlarge |
| 文本创作/翻译 | 1000~10000 | 1K~32K | 中并发 | **高** (流式阅读) | **高** | 5~60s | xlarge~xxlarge |
| 多模态 (图像理解) | 100~1000 | 大 (含图像 token) | 中并发 | 中 | 中 | 1~10s | medium~xlarge |
| 视频理解/生成 | 100~500 (描述) 或大 (视频 token) | 超大 | 低并发、长连接 | 低 | 中 | 10~300s | heavy (超长连接) |

### 详细场景分析与协议推荐

#### 1. 聊天对话 (ChatBot)

```
特征：输出 50~300 tokens，用户实时看流式输出，TTFT 直接决定体验
并发：高 (数百~数千 QPS)，短连接密集
瓶颈：首 token 延迟 → 协议建连 + 后端推理
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 3~10ms | **3ms** | light/10K |
| Req/s | 1880 | 1837 | light/10K |
| P99 | 306ms | **289ms** | light/10K |

**推荐：h2c→h2c** 或任意方案。Light 级别协议差异 <5%，但 h2c→h2c 的 P99 尾延迟最稳定，在用户量上涨时有更好的尾部表现。

#### 2. RAG 问答 (检索增强生成)

```
特征：输出 100~500 tokens，输入较长 (含检索文档)
并发：中等，请求间隔相对规律
瓶颈：prefill 耗时较长 (输入 token 多)，TTFT 包含推理 prefill 时间
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 162ms | **3.1ms** | heavy/10K |
| Req/s | 375 | **791** | heavy/10K |
| P99 | 4.04s | **666ms** | heavy/10K |

**推荐：h2c→h2c**。后端 h2c 消除 HOL Blocking 是关键——RAG 的 prefill 时间长，h1 连接被长时间占用后排队严重。

#### 3. SWE — 代码生成/补全 (Copilot 类)

```
特征：输出 200~2000 tokens，IDE 内用户在等待
并发：中高，突发性强 (用户按 Tab 触发)
瓶颈：TTFT 极敏感 (>500ms 用户就会取消)，需要快速开始流式输出
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 225ms | **2.4ms** | xlarge/10K |
| Req/s | 157 | **371** | xlarge/10K |
| P99 | 6.90s | **1.69s** | xlarge/10K |

**推荐：h2c→h2c (强烈推荐)**。

TTFT 225ms vs 2.4ms，差 94 倍。在 IDE 场景用户对延迟极为敏感——Copilot 类产品的核心体验指标就是 TTFT。h1→h1 的 P99 6.9s 意味着 1% 的用户要等近 7 秒才开始看到代码输出，在 IDE 中完全不可接受。

#### 4. SWE — 代码审查/大规模重构

```
特征：输出 500~5000 tokens，输入极长 (整个文件/仓库上下文)
并发：低 (通常单任务)
瓶颈：总吞吐量，长时间 SSE 流
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 1.15s | **5.4ms** | xxlarge/10K |
| Req/s | 60 | **83** | xxlarge/10K |
| Tok/s | 599K | **830K** | xxlarge/10K |
| 失败数 | **49** | 0 | xxlarge/10K |

**推荐：h2c→h2c**。h1→h1 在 xxlarge 出现超时失败，长流场景 HOL Blocking 致命。如果后端不支持 h2c，用 h2c→h1 也可 (408 Req/s, 0失败)。

#### 5. Agentic — Tool Use / Function Calling (ReAct/AutoGPT 类)

```
特征：多轮对话，每轮 50~500 tokens，轮与轮之间有链式依赖
并发：极高 (N 个 Agent × M 轮 × K 个并行 tool call)
瓶颈：TTFT (链式调用放大延迟) + 吞吐 (并发爆发)
      如果每轮 TTFT 增加 100ms，10 轮就多 1s
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 9.8ms | **2.3ms** | medium/10K |
| Req/s | 1055 | **1162** | medium/10K |
| P99 | 511ms | **449ms** | medium/10K |

**推荐：h2c→h2c (强烈推荐)**。

Agentic 场景的特殊性在于 **TTFT 的乘数效应**：一个 Agent 的 10 轮调用，每轮 TTFT 累加。h1→h1 每轮 9.8ms × 10 轮 = 98ms 额外延迟；h2c→h2c 每轮 2.3ms × 10 轮 = 23ms。在复杂 Agent 流程中 (20~50 轮)，差距被放大到秒级。

同时 Agentic 的并发模式是**突发性极强**——多个 Agent 同时发起 tool call，连接池压力瞬间拉满。h2c 的多路复用天然适合这种突发并发。

#### 6. Agentic RL — 强化学习训练 (RLHF/GRPO Rollout)

```
特征：batch rollout，同时向 N 个模型发送 M 条 prompt，收集输出
并发：超高 (batch_size × num_rollouts，可达数千)
延迟敏感度：TTFT 不敏感 (训练流程)，总吞吐决定训练速度
请求持续时间：1~20s (中等~长输出)
```

| 指标 | h1→h1 | h2c→h2c | h2c→h1 | 数据来源 |
|------|-------|---------|--------|---------|
| Req/s | 157 | 371 | **408** | xlarge/10K |
| Tok/s | 157K | 371K | **408K** | xlarge/10K |
| GRΔ | +1285 | **-1517** | +1540 | xlarge/10K |
| Heap Δ | +58.7MB | **+11.0MB** | +44.4MB | xlarge/10K |

**推荐：h2c→h2c 或 h2c→h1**。

RL 训练的核心指标是 **Tok/s (总 token 吞吐)**，因为它直接决定 rollout 速度。h2c→h1 在 xlarge 级别吞吐最高 (408K tok/s)，因为 h1 后端无帧开销。但 h2c→h2c 的 goroutine 开销最小 (Heap +11MB vs +58.7MB)，在超大 batch 场景下内存压力更小。

**特别注意**：RL 训练场景并发度往往远超 500 (batch=256 × rollout=4 = 1024+)，此时 h1 后端的连接池更容易耗尽。建议：
- batch_size ≤ 500：h2c→h1 (吞吐优先)
- batch_size > 500：h2c→h2c (避免连接池耗尽)

#### 7. 长文本摘要/分析

```
特征：输入极长 (32K~200K tokens)，输出中等 (500~3000 tokens)
并发：低 (通常批处理)
瓶颈：prefill 时间极长，单请求可能持续 10~60s
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 1.15s | **5.4ms** | xxlarge/10K |
| P99 | 35.8s | **6.4s** | xxlarge/10K |
| 失败数 | **49** | 0 | xxlarge/10K |

**推荐：h2c→h2c**。长文本摘要的 prefill 阶段会长时间占用 h1 连接，导致 HOL Blocking。h1→h1 在 xxlarge/10K 已经出现超时失败。对于 >100K tokens 输入，客户端超时需要设置得更长 (建议 300s+)。

#### 8. 文本创作/翻译 (长输出)

```
特征：输出 1000~10000 tokens，用户边看边读流式输出
并发：中等
瓶颈：TTFT (用户在等开头) + 持续吞吐 (流式阅读体验)
```

| 指标 | h1→h1 | h2c→h2c | 数据来源 |
|------|-------|---------|---------|
| TTFT | 225ms | **2.4ms** | xlarge/10K |
| Tok/s | 157K | **371K** | xlarge/10K |
| P99 | 6.90s | **1.69s** | xlarge/10K |

**推荐：h2c→h2c**。用户看流式输出，TTFT 和持续流畅度都重要。h1→h1 的 225ms TTFT 和 6.9s P99 会导致"卡顿-突然涌出一大段"的体验，h2c→h2c 的 2.4ms TTFT + 稳定 P99 保证平滑流式输出。

#### 9. 多模态 — 图像理解 (视觉问答/OCR)

```
特征：输入含图像 token (通常 576~2048 image tokens)，输出 100~1000 tokens
并发：中等
瓶颈：图像编码的 prefill 时间较长，但输出与文本场景类似
```

**推荐：h2c→h2c**。与 RAG/SWE 场景类似，prefill 时间长 + 中等输出。协议选型逻辑不变——输出 token 数决定了对应的测试级别 (medium~xlarge)。

#### 10. 视频理解/生成

```
特征：
  - 视频理解：输入超大 (视频帧 → 数万 image tokens)，输出中等 (描述/分析)
  - 视频生成：输出超大 (视频 token 流)，单请求持续数分钟
并发：极低 (GPU 资源密集)
瓶颈：极长连接持续时间 (30s~300s+)
```

**推荐：h2c→h2c，备选 hijack→h2c**。

视频场景的特殊性是**超长连接**。h1→h1 在超长 SSE 流中独占连接导致连接池耗尽。h2c 后端的多路复用是必需的。

hijack→h2c 在此场景值得考虑——视频通常是**少量长连接** (而非大量短连接)，此时 hijack 杀死 Keep-Alive 的缺点被摊薄，而 TCP_NODELAY 的低延迟 flush 有利于视频帧的实时传输。

### 场景协议速查表

| 场景 | 推荐协议 | 关键理由 | 对应测试级别 | TTFT 基准 |
|------|---------|---------|------------|----------|
| 聊天对话 | h2c→h2c | P99 尾延迟最优 | light | 3ms |
| RAG 问答 | h2c→h2c | 消除 prefill 期间的 HOL Blocking | medium~heavy | 3ms |
| SWE 代码补全 | **h2c→h2c** | TTFT 2.4ms vs 225ms，IDE 体验关键 | medium~xlarge | 2.4ms |
| SWE 代码审查 | h2c→h2c | 长流零失败 | heavy~xxlarge | 5ms |
| Agentic Tool Use | **h2c→h2c** | TTFT 乘数效应 + 突发并发 | light~heavy | 2.3ms |
| Agentic RL 训练 | h2c→h2c / h2c→h1 | 吞吐优先，大 batch 用 h2c→h2c | medium~xlarge | 不敏感 |
| 长文本摘要 | h2c→h2c | 超长 prefill，h1 会超时失败 | heavy~xxlarge | 5ms |
| 文本创作/翻译 | h2c→h2c | 流式阅读体验 | xlarge~xxlarge | 2.4ms |
| 多模态图像 | h2c→h2c | 图像 prefill 长，同 RAG 逻辑 | medium~xlarge | 3ms |
| 视频理解/生成 | h2c→h2c / hijack→h2c | 超长连接，少量并发 | heavy (超长) | 不敏感 |

### 一句话总结

> **除非有明确的兼容性约束，所有大模型推理场景都应使用 h2c→h2c。** h2c 消除了 HTTP/1.1 的 Head-of-Line Blocking 和连接独占问题——这正是 SSE 长流场景的核心痛点。唯一需要权衡的是 h2c→h1 在特定吞吐密集场景 (RL 训练) 下因少一层帧序列化而略快，但差距在 10% 以内。

## 三、Go HTTP 框架选型：hertz / fiber / fasthttp vs gin / net/http

### 3.1 架构差异

| 维度 | net/http (gin) | fasthttp (fiber) | hertz |
|------|---------------|-------------------|-------|
| 网络模型 | goroutine-per-connection | worker goroutine pool 复用 | netpoll (epoll/kqueue) 事件驱动 |
| 内存分配 | 每请求新建 `Request`/`Response` | `RequestCtx` 对象池复用，零拷贝 header 解析 | gopkg 零拷贝 + 对象池 |
| 连接管理 | 1 goroutine = 1 connection | worker pool 复用连接 | epoll 多路复用，idle 连接几乎零开销 |
| GC 压力 | 高（大量短生命周期对象） | 低（对象池 + `[]byte` 原地操作） | 低 |
| 短请求吞吐上限 | ~10 万 QPS | ~30-50 万 QPS | ~30-50 万 QPS |
| HTTP/2 支持 | **原生支持**（h2 + h2c） | **不支持** | **不支持** |
| SSE 实现 | `http.Flusher` 标准接口 | `SetBodyStreamWriter(func(*bufio.Writer))` | 需 `io.Pipe` + `SetBodyStream` 间接实现 |

### 3.2 核心优势

fasthttp / fiber / hertz 相对于 net/http / gin 的性能优势来自三个层面：

1. **对象池复用** → GC 暂停减少 50%+，吞吐更稳定
2. **`[]byte` 零拷贝解析** → 内存分配降低 80%+，减少 runtime.mallocgc 开销
3. **Worker pool / netpoll** → goroutine 数量可控，不随连接数线性增长

**典型收益场景**：高并发短请求（JSON API、静态文件、代理转发），吞吐量可达 net/http 的 3~10 倍。

### 3.3 适用场景对比

| 场景 | 推荐框架 | 理由 |
|------|---------|------|
| 高 QPS JSON API（>10万） | fasthttp / fiber / hertz | 对象池 + 零拷贝，每请求开销极低 |
| 大量 idle 长连接 (推送/通知) | hertz (netpoll) | epoll 事件驱动，idle 连接不占 goroutine |
| REST API 常规业务 | gin / net/http | 生态完善、中间件丰富、性能足够 |
| 需要 HTTP/2 / gRPC | **net/http (唯一选择)** | fasthttp/fiber/hertz 均不支持 HTTP/2 |
| SSE 流式传输 (LLM 推理) | **net/http** | 见下文分析 |

### 3.4 LLM SSE 场景：框架差异为何消失

在本次基准测试中，4 个框架在 SSE 流式场景下性能差异 **< 5%**。原因：

```
SSE 请求耗时 = token 生成等待 (~250ms~10s) + 框架层开销 (~0.01~0.1ms)
                   ↑ 占 99.9%+                      ↑ 占 <0.1%
```

SSE 的性能瓶颈在 **token 生成的 IO 等待**，而非框架层的请求解析/响应序列化。fasthttp 的零拷贝、对象池在此场景几乎无意义——每个请求持续数百毫秒到数十秒，框架层 overhead 被完全掩盖。

此外，SSE 场景的 API 适配度也不同：

| 框架 | SSE 实现方式 | 适配度 |
|------|------------|--------|
| **net/http** | `http.Flusher` 标准接口，每写一次 `Flush()` | 原生支持，简洁稳定 |
| **gin** | 基于 net/http，完全继承 `Flusher` | 原生支持 |
| **fasthttp** | `SetBodyStreamWriter(func(w *bufio.Writer))` | 可用，但 API 非标准 |
| **fiber** | 底层调用 fasthttp 的 `StreamWriter` | 同 fasthttp |
| **hertz** | 需用 `io.Pipe` + `SetBodyStream` 间接实现 | **无原生 StreamWriter**，需额外 goroutine + pipe |

### 3.5 致命短板：HTTP/2 SSE 不可用

这是 LLM SSE 网关选型中最关键的约束：

| 框架 | HTTP/2 支持 | SSE over HTTP/2 |
|------|-----------|-----------------|
| **net/http** | 原生支持（h2 + h2c） | **完全支持** |
| **gin** | 基于 net/http，原生支持 | **完全支持** |
| **fasthttp** | **不支持** | **不可用** |
| **fiber** | **不支持**（底层是 fasthttp） | **不可用** |
| **hertz** | **不支持**（底层是 netpoll） | **不可用** |

而本报告的协议基准测试已经证明，**HTTP/2 (h2c) 是 LLM SSE 的最优协议**：

| 对比指标 (heavy/10K) | h1→h1 | h2c→h2c | 差距 |
|---------------------|-------|---------|------|

| Req/s | 375 | **791** | **2.1 倍** |
| P99 | 4.04s | **666ms** | **6.1 倍** |
| 超时失败 (xxlarge/10K) | 49 | **0** | — |

使用 fasthttp/fiber/hertz 意味着**永远锁死在 HTTP/1.1**，放弃多路复用带来的巨大收益。

| xxlarge | 5.0ms | **62.0ms** | **12x** |

> **关键发现**：
> 1. **h1 前端吞吐**：hertz proxy 与 nethttp proxy 基本持平 (±5%)，heavy/xlarge 场景 hertz 反而更好因 netpoll 的连接处理效率
> 2. **h2c 前端吞吐**：hertz proxy 与 nethttp proxy 差异不大 (±12%)
> 3. **h2c 前端 TTFT 致命缺陷**：hertz-contrib/http2 的 SetBodyStream 在 h2c 模式下缓冲首帧，TTFT 退化 12~137 倍
> 4. **hertz proxy h1 前端 P99**：heavy+ 场景 P99 显著高于 nethttp (io.Pipe 背压 + 额外 goroutine)
> 5. **内存开销**：hertz proxy 因 io.Pipe 机制，PeakGR 和 Heap 开销略高

### 3.8 结论

```
fasthttp / fiber / hertz 适合：高 QPS 短请求（JSON API、代理转发）— 框架开销是瓶颈
fasthttp / fiber / hertz 不适合：LLM SSE 网关 — 因为：
  1. SSE 场景框架层开销占比 <0.1%，换框架无吞吐收益
  2. 不支持 HTTP/2，丧失多路复用 → 高并发下 TTFT 劣化 52~213 倍
  3. SSE API 非标准，hertz 甚至需要 io.Pipe workaround
  4. hertz 在超大输出 (10K tokens) 下 io.Pipe 背压导致性能崩溃 (吞吐降 87~90%)
  5. [新增] hertz 作为 proxy 框架：h1 前端吞吐持平，但 h2c 前端 TTFT 退化 12~137 倍
  6. [新增] hertz-contrib/http2 的 SetBodyStream 在 h2c 模式下无法及时 flush 首帧

hertz 作为 proxy 框架的额外问题：
  - h1 前端：吞吐与 nethttp 持平 (±5%)，但 P99 尾延迟更高 (io.Pipe 背压)
  - h2c 前端：吞吐持平，但 TTFT 灾难性退化 (277ms vs 2.6ms @ light)
  - hertz-contrib/http2 已归档 (2026-01-29)，不再维护

LLM 推理 SSE 网关的正确选型：
  ✓ net/http (或 gin) + h2c → 原生 HTTP/2 多路复用 + 标准 Flusher 接口
  ✗ fasthttp / fiber / hertz → 微秒级框架优化 vs 毫秒~秒级协议劣势
  ✗ hertz 作为 proxy 也不行 → h2c TTFT 退化 + io.Pipe 尾延迟 + 归档依赖
```

> **一句话：对 LLM SSE 场景，不要追求框架层的微秒级优化，应该追求协议层 (HTTP/2) 的毫秒到秒级优化。fasthttp / fiber / hertz 因不支持 HTTP/2，在 LLM SSE 场景下反而是劣势选择。实测数据进一步表明：即使用 hertz 做 proxy 框架 (而非后端)，h2c 前端的 TTFT 仍退化 12~137 倍，hertz-contrib/http2 已归档不再维护。**

| h1→h1, xxlarge/10K | 49 | 0.49% | HOL Blocking 排队，部分请求总耗时超 120s 客户端超时 |

---

## 七、机制解释

### 7.1 h1 后端大数据量退化的根因：HOL Blocking

HTTP/1.1 每条 TCP 连接同一时间只能承载一个请求。当 SSE 流长时间占用连接不释放时，proxy 的连接池被耗尽，后续请求必须排队等待。

```
# h1 后端: 每个 SSE 流独占一条连接
TCP Conn 1: [──── SSE Stream A (1s) ────][ SSE Stream D ... ]
TCP Conn 2: [──── SSE Stream B (1s) ────][ SSE Stream E ... ]
TCP Conn 3: [──── SSE Stream C (1s) ────][ 排队等待... ]

# h2c 后端: 多条 stream 共享一条连接
TCP Conn 1: [Stream A] [Stream B] [Stream C] [Stream D] [Stream E] ...
                ↓ 无需等待，立即开始
```

这解释了 xlarge (1Ktok) 场景 h1→h1 仅 85 Req/s (理论 500)，而 h1→h2c 达到 312 Req/s (+267%)。

### 7.2 h2c 前端 TTFT 最优的原因

h2c→h2c 的 TTFT 在所有数据量下稳定在 2~10ms，原因：

1. **无需 TCP 握手**：HTTP/2 多路复用在现有连接上直接开 stream，省去三次握手延迟
2. **帧级别交付**：第一个 DATA 帧到达即可交付应用层，无需等 HTTP/1.1 chunked encoding 解析
3. **无协议转换**：全链路 h2c 时 proxy 无需 h1↔h2 转换，减少一次 buffer copy

### 7.3 hijack 在短连接场景的劣势

Hijack 接管裸 TCP 连接后，HTTP Keep-Alive 失效，每个请求都需要：
1. TCP 三次握手 (localhost ~0.1ms，但有内核调度延迟)
2. 内核分配新 socket buffer
3. 无法复用之前的连接

在请求密集时形成"连接风暴"。但在**长期保持的单一 SSE 连接**中 (如真实 LLM 推理场景，一个请求持续数秒)，连接建立开销被摊薄，hijack 的 TCP_NODELAY 低延迟 flush 优势才能体现。

### 7.4 为什么 h2c→h1 有时吞吐高于 h2c→h2c？

heavy/1K 中 h2c→h1=821 Req/s > h2c→h2c=749 Req/s。原因：

- h2c→h2c 全链路 HTTP/2 有**两层帧序列化开销** (前端帧 + 后端帧)
- h2c→h1 后端是简单的流式字节传输，无帧开销
- 当连接池足够大时，h1 后端的 HOL Blocking 还未完全触发
- 但在 10K 请求持续压力下 h2c→h2c (791) 追平 h2c→h1 (788)，连接复用最终占优

benchmarks/sse-bench/                  # 独立 Go module，与主项目依赖隔离

│   └── bench.go                       # 基准测试客户端 (HTTP/1.1 + h2c)

│   ├── proxy.go                       # SSE 反向代理 (standard/hijack × h1/h2c, net/http)

│   ├── fiber_server.go                # fiber 服务器
