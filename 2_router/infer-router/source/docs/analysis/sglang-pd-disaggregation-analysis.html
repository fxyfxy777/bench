📖 1. 概述与设计动机

核心思想

PD分离将LLM推理的两个阶段——Prefill（预填充）和Decode（解码）——分离到不同物理节点执行，通过高速网络（RDMA/NVLink）传输KV Cache，实现各阶段独立扩缩容和硬件针对性优化。

为什么需要PD分离？

维度Prefill阶段Decode阶段
计算特征计算密集型 — 并行处理全部input tokens内存带宽密集型 — 自回归逐token生成
GPU利用率高算力利用率，FLOPS饱和低算力利用率，受制于显存带宽
延迟特征取决于input长度（TTFT）取决于输出长度（TPS）
扩缩需求按并发prompt数扩缩按在线并发请求数扩缩
硬件优化适合高算力GPU（H100 SXM）适合高带宽/大显存GPU

⚠️ 关键权衡

PD分离引入KV Cache网络传输开销。只有当网络传输延迟 < Prefill与Decode混合调度的资源争抢延迟时，才有收益。SGLang通过RDMA实现亚毫秒级KV传输使收益显著。

🎯 3. Router核心设计 重点

设计哲学

Router不参与任何计算或数据传输，仅负责请求的选路和协调。通过注入bootstrap元数据让Prefill和Decode自行建立直接连接。

3.1 双发模式（Dual Dispatch）

SGLang PD Router的核心是双发模式：同一请求被同时发送到Prefill和Decode。这不是串行的"先P再D"，而是并行发送，两端通过bootstrap自行协调。

Dual Dispatch Sequence Flow

双发执行核心逻辑

// execute_dual_dispatch 简化流程
async fn execute_dual_dispatch(&self, request, route, ctx) -> Response {
    RetryExecutor::execute_response_with_retry(|attempt| {
        let (prefill, decode) = self.select_pd_pair(&ctx)?;

        let body = inject_bootstrap_into_value(
            &request_json,
            &prefill.host(),        // bootstrap_host = prefill的IP
            prefill.bootstrap_port, // bootstrap_port = 8998
            batch_size,
        );

        // 同时发送给两个worker（tokio::join!并行）
        let (prefill_resp, decode_resp) = tokio::join!(
            send_to_worker(&prefill, &body),
            send_to_worker(&decode, &body),
        );

        merge_responses(prefill_resp, decode_resp)
    })
}

3.2 Bootstrap元数据注入

Router为每个请求生成唯一的"会面点"信息，注入到请求JSON中：

字段类型来源用途
bootstrap_hostString从Prefill worker URL提取hostnameDecode连接Prefill Bootstrap Server的地址
bootstrap_portOption<u16>Prefill注册时提供（默认8998）Bootstrap Server端口
bootstrap_roomu64rand::random::<u64>() & (i64::MAX as u64)唯一KV传输会话的Room ID
// pd_types.rs - Room ID 生成（[0, 2^63-1] 范围，与Python端一致）
pub fn generate_room_id() -> u64 {
    rand::random::<u64>() & (i64::MAX as u64)
}

// 注入逻辑：批量请求注入数组，单请求注入标量
fn inject_bootstrap_into_value(body: &mut Value, host: &str, port: Option<u16>, batch: Option<usize>) {
    match batch {
        Some(n) => {
            body["bootstrap_host"] = json!(vec![host; n]);
            body["bootstrap_port"] = json!(vec![port; n]);
            body["bootstrap_room"] = json!((0..n).map(|_| generate_room_id()).collect::<Vec<_>>());
        }
        None => {
            body["bootstrap_host"] = json!(host);
            body["bootstrap_port"] = json!(port);
            body["bootstrap_room"] = json!(generate_room_id());
        }
    }
}

3.6 RAII负载追踪

// 使用 Drop trait 自动管理并发计数（流式响应安全）
struct WorkerLoadGuard { worker: Arc<Worker> }

impl WorkerLoadGuard {
    fn new(w: &Arc<Worker>) -> Self {
        w.load.fetch_add(1, Ordering::Relaxed);  // 请求开始 +1
        Self { worker: w.clone() }
    }
}
impl Drop for WorkerLoadGuard {
    fn drop(&mut self) {
        self.worker.load.fetch_sub(1, Ordering::Relaxed);  // 请求结束 -1
    }
}
// Guard附着ResponseBody → 流完成/中断自动释放 → 精确追踪SSE连接

# decode.py - 关键：Decode预分配GPU内存，告诉Prefill写到哪里
def _pre_alloc(self, req):
    # 计算page数（input tokens + 预留decode tokens）
    num_pages = get_num_new_pages(req.extend_input_len + num_reserved_decode_tokens, page_size)

    # 可选：Decode端Radix Cache匹配已有前缀
    if decode_enable_radix_cache:
        prefix_len = match_prefix_for_req(req, radix_cache)
        num_pages -= prefix_len // page_size

    # 从Decode KV Pool分配空闲pages
    allocated_indices = token_to_kv_pool.alloc(num_pages)

    # 通过ZMQ告诉Prefill "写到这些位置"
    req.kv_receiver.send_metadata(
        kv_indices=allocated_indices,
        aux_index=req.metadata_buffer_idx,
        decode_prefix_len=prefix_len,
    )

🔀 8. 与RL-Router设计的对比参考

8.1 架构模式对比

SGLang PD模式

  • Router：纯转发 + 元数据注入（无状态）
  • 调度：双发（同一请求同时给P和D）
  • 状态：P/D自行协调，Router不持有
  • KV传输：P→D直接RDMA
  • 负载感知：原子计数器（RAII Guard）
  • 容错：重试选新pair + 熔断器

RL-Router当前模式

  • Router：中心Scheduler + 分布式Gateway
  • 调度：Scheduler分配 → Gateway转发
  • 状态：Scheduler全局状态，Gateway心跳上报
  • KV传输：待设计
  • 负载感知：event-loop全局汇聚
  • 容错：心跳超时清理 + 重注册

8.2 可借鉴的设计模式

1. Bootstrap Room 机制

为每个请求生成唯一 room ID 作为P和D的"会面点"。Router只注入ID不维护P-D连接状态。
→ RL-Router：Scheduler分配请求时使用类似"ticket"，Gateway和后端通过ticket建立一对一映射。

2. 独立策略注册表

Prefill和Decode使用不同负载均衡策略，通过PolicyRegistry统一管理但独立执行。
→ RL-Router：Scheduler为P/D实例维护独立调度策略，支持运行时动态切换。

3. RAII 负载追踪

Guard模式自动管理负载计数：请求开始+1，结束（含流式）-1。
→ RL-Router：Gateway代理开始隐式Allocate，结束隐式Release，避免显式RPC可靠性问题。

4. 传输状态机

KVPoll五状态清晰定义传输阶段，方便超时检测和错误恢复。
→ RL-Router：定义类似状态机 Scheduling → Prefilling → Transferring → Decoding → Complete。

5. Bootstrap Server（侧信道协调）

轻量HTTP服务作为P-D间"黄页"，提供rank信息查询和room注册。
→ RL-Router：Scheduler本身承担此角色，Gateway通过Scheduler查询目标P/D连接信息（拉取模式更灵活）。

8.3 SGLang方案的局限性

⚠️ RL-Router需要改进的方面

  1. Router无全局视角 — SGLang仅有worker级负载计数，无request级全局调度视角
  2. P-D选择无拓扑感知 — 独立选择P和D不考虑网络距离，跨机房可能延迟高
  3. 无队列管理 — 所有请求直接转发，过载时依赖后端自身队列
  4. 无Step隔离 — 面向持续服务，不支持训练场景的每轮隔离
  5. 双发带宽浪费 — 长prompt请求体发两次，可优化为只发metadata给D

8.4 RL-Router PD重设计建议

推荐架构思路

结合SGLang高效传输 + RL-Router全局调度：

  1. Scheduler全局PD调度 — 知道所有P/D负载，做全局最优pair分配（可考虑拓扑亲和性）
  2. Gateway透传+协调 — 向Scheduler申请PD pair → 返回(P, D, room_id) → Gateway双发或串行
  3. KV传输走sidecar — 复用SGLang RDMA/Mooncake机制，Router/Gateway不参与数据面
  4. Step隔离 — 每Step开始预分配P/D资源，结束统一释放
  5. 请求状态机 — Scheduler维护每请求PD状态机，超时自动重试/failover
